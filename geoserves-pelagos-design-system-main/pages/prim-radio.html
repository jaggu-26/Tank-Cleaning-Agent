Radio Button

Overview

Radio buttons let users select exactly one option from a group. Unlike checkboxes, selecting one radio automatically deselects any previously selected option in the same group. Use them in forms and settings panels where mutual exclusivity is a hard requirement.

Anatomy

The radio button is a 24×24px touch container holding a 16×16px outer ring and an 8×8px inner dot. A 2px gap separates the control from the label.

  1. Touch target — 24×24px invisible hit area wrapping the visual control. Meets accessibility minimum with outer padding.
  2. Outer ring — 16×16px circle, border-radius: 50%, 1.5px border. Gray (#cbd5e1) when unselected; brand blue (#1852fe) when selected.
  3. Gap — 2px spacing between ring and label. From --spacing/spacing-2.
  4. Label — 14px / Regular / 20px line-height in #10172a. Required for accessible usage; icon-only radios must carry aria-label.
Inner dot: 8×8px solid circle sits centered inside the outer ring. Hidden (scale(0)) when unselected; full size (scale(1)) when selected. Transitions with 120ms ease for a smooth snap-in feel.

Interaction Behaviour

Clicking anywhere on the label or ring selects that radio and deselects the previously selected one in the group. Only the selected state can be set via click — once a radio group has a selection, it cannot be deselected by clicking again.

Accessibility

Radio buttons have strong native semantics. Always use the native <input type="radio"> — avoid ARIA role overrides unless absolutely necessary.

RequirementImplementation
Group labellingWrap all options in a <fieldset> with a <legend>. Screen readers announce the legend before each option.
Option labellingEach <input> is wrapped in a <label> or linked via for/id. No icon-only radios without aria-label.
Keyboard navigationArrow keys move within a group. Tab moves between groups. Do not trap focus.
Disabled stateUse native disabled attribute. Do not rely on CSS pointer-events: none alone — assistive technologies bypass CSS.
Error statesUse aria-describedby to link error messages. Mark the fieldset with aria-invalid="true".
Color contrastRing border (#1852fe) on white: 4.6:1. Dot on ring background: visually large enough (> 3:1). Label text: 14.8:1.

Overview

The RadioButton component renders a native <input type="radio"> styled via CSS class tokens. Group multiple instances with a shared name prop to enforce mutual exclusivity. The component is uncontrolled by default and supports a controlled value API.

JSX
{/* Uncontrolled */}
<RadioButton name="plan" value="starter" label="Starter" defaultChecked />
<RadioButton name="plan" value="pro"     label="Pro" />
<RadioButton name="plan" value="enterprise" label="Enterprise" />

{/* Controlled */}
const [plan, setPlan] = useState('starter');
<RadioButton name="plan-ctrl" value="starter"    label="Starter"    checked={plan==='starter'}    onChange={()=>setPlan('starter')} />
<RadioButton name="plan-ctrl" value="pro"        label="Pro"        checked={plan==='pro'}        onChange={()=>setPlan('pro')} />
<RadioButton name="plan-ctrl" value="enterprise" label="Enterprise" checked={plan==='enterprise'} onChange={()=>setPlan('enterprise')} />
HTML
<!-- Template-driven -->
<gs-radio-group name="plan" [(ngModel)]="selectedPlan">
  <gs-radio value="starter">Starter</gs-radio>
  <gs-radio value="pro">Pro</gs-radio>
  <gs-radio value="enterprise">Enterprise</gs-radio>
</gs-radio-group>

Full Working Example

Complete, production-ready component with validation, accessibility, and all states.

JSX
import { useState } from 'react';
import { RadioGroup, RadioButton } from '@pelagos/design-system';

const PLANS = [
  { value: 'starter',    label: 'Starter',    description: 'Up to 5 users' },
  { value: 'pro',        label: 'Pro',         description: 'Up to 50 users' },
  { value: 'enterprise', label: 'Enterprise',  description: 'Unlimited users' },
  { value: 'custom',     label: 'Custom',      description: 'Contact sales', disabled: true },
];

export function PlanPickerForm() {
  const [plan, setPlan]   = useState('pro');
  const [error, setError] = useState('');

  function handleSubmit(e) {
    e.preventDefault();
    if (!plan) { setError('Please select a plan.'); return; }
    setError('');
    console.log('Selected plan:', plan);
  }

  return (
    <form onSubmit={handleSubmit} noValidate>
      <RadioGroup
        name="plan"
        legend="Select a plan"
        value={plan}
        onChange={(v) => { setPlan(v); setError(''); }}
        aria-invalid={!!error}
        aria-describedby={error ? 'plan-error' : undefined}
      >
        {PLANS.map((p) => (
          <RadioButton
            key={p.value}
            value={p.value}
            label={p.label}
            disabled={p.disabled}
          />
        ))}
      </RadioGroup>

      {error && (
        <span id="plan-error" role="alert" style={{ color: '#dc2626', fontSize: 13 }}>
          {error}
        </span>
      )}

      <button type="submit" style={{ marginTop: 16 }}>Confirm plan</button>
    </form>
  );
}
TS
import { Component } from '@angular/core';
import { FormBuilder, Validators, ReactiveFormsModule } from '@angular/forms';
import { GsRadioModule } from '@pelagos/design-system-angular';

@Component({
  selector: 'app-plan-picker',
  templateUrl: './plan-picker.component.html',
  standalone: true,
  imports: [ReactiveFormsModule, GsRadioModule],
})
export class PlanPickerComponent {
  plans = [
    { value: 'starter',    label: 'Starter',   disabled: false },
    { value: 'pro',        label: 'Pro',        disabled: false },
    { value: 'enterprise', label: 'Enterprise', disabled: false },
    { value: 'custom',     label: 'Custom',     disabled: true },
  ];

  form = this.fb.group({
    plan: ['pro', Validators.required],
  });

  constructor(private fb: FormBuilder) {}

  get planError(): boolean {
    const ctrl = this.form.get('plan');
    return !!ctrl?.invalid && !!ctrl?.touched;
  }

  onSubmit() {
    this.form.markAllAsTouched();
    if (this.form.invalid) return;
    console.log('Selected plan:', this.form.value.plan);
  }
}

On This Page

When to Use
  • Single selection from a group — When the user must pick exactly one option (billing period, shipping method, account type). The mutual exclusivity of radios communicates that only one value is valid.
  • 2–7 visible options — When the full set fits on screen without scrolling. Fewer than 2 options is trivial (use a toggle); more than 7 should become a Select/Dropdown for scannability.
  • Comparing options side-by-side — Settings panels where all choices must be visible simultaneously so the user can compare before deciding.
  • Form fields requiring explicit commitment — Role selection, plan selection, gender/title fields, scheduling recurrence. Radio buttons make it clear that the form cannot be submitted until one is chosen.
  • Filters with mutually exclusive values — "Show: All / Active / Archived" — only one filter state applies at a time.
When Not to Use
  • Multi-select scenarios — Use instead. If the user can pick more than one option simultaneously, checkboxes communicate that independence.
  • On/Off toggle — Use instead. Two radios labeled "On" and "Off" is an anti-pattern; a toggle communicates binary switching and immediate effect more directly.
  • Long option lists (8+) — Use a Select / Dropdown instead. Vertical lists of many radios push content down the page and make scanning difficult.
  • Already-known default with rare change — If one option is correct 95% of the time and users rarely override it, consider a default setting with an explicit override control rather than presenting all options as equal.
  • Inline in dense table cells — Use Checkbox for row selection in tables. Radios in a table column suggest only one row can be selected at a time, which may not be the intent.
Content Hierarchy
Label Writing Rules
  • Use a noun or noun phrase — "Monthly", "Annual", "Enterprise". Avoid verb forms since selecting a radio is a choice, not an action.
  • Sentence case — "Pay annually" not "Pay Annually". Exception: proper nouns and acronyms.
  • Keep labels parallel — All options in a group should follow the same grammatical form. Mix of "Monthly billing" and "Annual" is inconsistent.
  • Short and scannable — 1–4 words ideal. Use a description line below the label (helper text) for additional context, not the label itself.
  • No trailing punctuation — Labels don't end with periods or colons.

For options that include a description line (e.g. pricing tiers), align the ring to the top of the first text line with align-items: flex-start and add margin-top: 2px to the ring for optical alignment with the cap-height.

Common Mistakes
❌ Mistake

Using different name attributes across radios that are logically a group — making multiple radios appear selected simultaneously.

✅ Fix

All options in a group must share the same name attribute. Use RadioGroup to enforce this automatically.

❌ Mistake

Using two radios for a binary Yes/No or On/Off choice.

✅ Fix

Use a Toggle for On/Off (immediate effect) or a Checkbox for Yes/No consent declarations. Radios imply the existence of more than two alternatives.

❌ Mistake

Omitting a <fieldset> / <legend> around the group — screen readers announce each option without knowing what it belongs to.

✅ Fix

Always wrap groups in a RadioGroup (which renders <fieldset> + <legend>). The legend provides the group label announced before each option.

❌ Mistake

Showing no pre-selected option when one default is clearly correct, forcing users to always make an explicit choice before proceeding.

✅ Fix

Set a sensible defaultChecked / defaultValue for the most common choice. Users who agree with the default skip it; others change it consciously.

❌ Mistake

Using a horizontal layout for long labels — options wrap unpredictably and become hard to associate with their radio.

✅ Fix

Use horizontal layout only when all labels are ≤3 words and there are ≤4 options. Otherwise, default to vertical stacking.
