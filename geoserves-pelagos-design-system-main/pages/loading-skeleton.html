Skeleton

Overview

Skeleton provides animated placeholder shapes that mirror the structure of incoming content — reducing perceived load time and preventing layout shift. It is built over the Ant Design Skeleton spec with GeoServe tokens applied to colour, radius, and timing. Use it for first-load states where the layout is known but the data is not yet available.

← Static (default) ← Active / animated

Anatomy

A full Skeleton is composed of up to four parts: avatar circle, title bar, paragraph rows, and the optional active shimmer overlay. Each part maps directly to an Ant Design sub-prop.

  1. Avatar — Optional circle (or square) placeholder. Enabled via avatar prop. Sizes: small (24px), default (32px), large (40px).
  2. Title — Single bar representing a heading. Height: 16px (titleHeight token). Width defaults to 38%; overridable.
  3. Paragraph rows — Stack of bars representing body text. Row height: 16px (paragraphLiHeight). Default: 3 rows. Gap above paragraph: 28px (paragraphMarginTop).
  4. Last paragraph row — Always rendered at 61% width by default to mimic natural text wrap. Override with paragraph.width array.
Variants

Five element variants mirror common content shapes. Combine Skeleton (paragraph), Skeleton.Avatar, Skeleton.Button, Skeleton.Input, and Skeleton.Image to replicate any layout.

Do / Don't
Do

  • Mirror the real content layout exactly — skeleton shape, size, and count should match the content it replaces.

  • aria-busy="true" on the parent region while loading

    Always set aria-busy on the surrounding content region so screen readers announce the loading state.

Don't
  • All rows equal width ✗

    Don't use equal widths on all paragraph rows — it looks mechanical. Vary widths (100%, 94%, 61%) for a natural feel.

  • Show skeleton + spinner simultaneously in the same region

    Don't mix Skeleton and Spinner in the same content area — choose one loading pattern per region.

Overview

The Skeleton component wraps Ant Design's Skeleton with GeoServe CSS tokens applied to colours, border radius, and animation timing. Sub-components — Skeleton.Avatar, Skeleton.Button, Skeleton.Input, and Skeleton.Image — are re-exported unchanged.

Apply the .skel-block utility class to any element, then wrap in .skel-active to enable animation. The CSS is available globally in styles.css — no module imports needed.

# antd is already a peer dependency of @pelagos/components

Include styles.css in your project — the .skel-block and .skel-active classes are globally available. No additional packages required.

Usage Patterns
JSX
// Pattern A — table row skeleton (always 3 rows)
{isLoading ? (
  [1,2,3].map(i => (
    <tr key={i} className="tbl-skeleton-row">
      <td><div className="tbl-skeleton-cell" style={{width:'46px'}} /></td>
      <td><div className="tbl-skeleton-cell" style={{width:'110px'}} /></td>
      <td><div className="tbl-skeleton-cell"
              style={{width:'80px', borderRadius:'20px'}} /></td>
    </tr>
  ))
) : rows.map(row => <TableRow key={row.id} row={row} />)}

// Pattern B — card grid skeleton
{isLoading ? (
  <div className="card-grid">
    {[1,2,3].map(i => (
      <Skeleton key={i} active avatar={{ shape:'square', size:'large' }}
               paragraph={{ rows: 2 }} />
    ))}
  </div>
) : <CardGrid items={items} />}

// Pattern C — form pre-fill skeleton
{isLoading ? (
  <div className="form-grid">
    {[1,2,3,4].map(i => (
      <div key={i}>
        <Skeleton.Input active size="large" block />
      </div>
    ))}
  </div>
) : <InquiryForm data={formData} />}

Follow the same three patterns in Angular — replace JSX with Angular structural directives (*ngIf) and map component references to .skel-block HTML equivalents. See the Variants section for the HTML patterns.

Full Example
JSX
import { useState, useEffect } from 'react';
import { Skeleton } from '@pelagos/components/loading/skeleton';

export function VesselCard({ vesselId }) {
  const [vessel, setVessel] = useState(null);
  const [loading, setLoading] = useState(true);
  const [showSkel, setShowSkel] = useState(false);

  // 300ms delay prevents flicker for fast connections
  useEffect(() => {
    const t = setTimeout(() => setShowSkel(loading), 300);
    return () => clearTimeout(t);
  }, [loading]);

  useEffect(() => {
    fetchVessel(vesselId).then(data => {
      setVessel(data);
      setLoading(false);
      setShowSkel(false);
    });
  }, [vesselId]);

  return (
    <section
      aria-busy={showSkel}
      aria-label="Vessel details"
    >
      <span className="sr-only" role="status" aria-live="polite">
        {showSkel ? 'Loading vessel details' : 'Vessel details loaded'}
      </span>

      <Skeleton
        active
        loading={showSkel}
        avatar={{ shape: 'circle', size: 'large' }}
        paragraph={{ rows: 3, width: ['100%', '85%', '61%'] }}
      >
        /* real content — shown when loading=false */
        <VesselDetail vessel={vessel} />
      </Skeleton>
    </section>
  );
}

On This Page

When to Use
  • First data load with a known layout — whenever the page structure is predictable (list of cards, table rows, form fields) and data is loading for the first time. The skeleton prevents layout shift by holding the exact space the content will occupy.
  • Parallel data fetching — when multiple sections fetch independently, show a skeleton per section. Each resolves into content at its own pace without blocking other parts of the UI.
  • Rich content areas — components that contain lots of information (Table, List, Card grid) benefit most from skeletons since they have a high surface area to fill.
  • Content that doesn't exist yet — use Skeleton to visualise placeholder layouts in empty states or "coming soon" panels.
When Not to Use
  • Background mutations — use inside buttons for save/approve/submit actions. A skeleton would imply full-section re-load which is misleading.
  • Unknown layout — if you can't predict the content shape (e.g. a rich-text article of variable length), use instead. A badly-proportioned skeleton is worse than no skeleton.
  • Very fast loads (<300ms) — showing a skeleton for 200ms then immediately replacing it with real content causes jarring visual flicker. Apply a 300ms delay before rendering the skeleton; if data arrives within that window, skip it entirely.
  • Deterministic progress — use when you can report a percentage (file upload, multi-step wizard).
Best Practices
  • Mirror real content dimensions exactly — the skeleton and the actual content must occupy the same space to prevent layout jump on reveal. Check that avatar size, row heights, and column widths match 1:1.
  • Vary paragraph row widths — use decreasing widths (100%, 94%, 61%) per Ant Design's default. Equal-width rows look mechanical; varying widths mimic natural prose.
  • Always 3 rows for Table skeletons — consistent with the Table component specification. Never vary the count based on expected result set size.
  • Apply a 300ms show-delay — render real content immediately; only show the skeleton if data hasn't resolved after 300ms. This eliminates flicker for fast connections without removing the feedback for slow ones.
  • Provide a 10s timeout fallback — if data hasn't arrived after 10 seconds, replace the skeleton with an error empty state that includes a retry action.
  • Set aria-busy on the region — not on the skeleton blocks themselves. The skeleton blocks should be aria-hidden="true".
Patterns
  • Table row pattern — use .tbl-skeleton-row and .tbl-skeleton-cell (pre-configured in the Table component). Always show 3 rows. Badge cells get border-radius: 20px, chip cells get border-radius: 6px.
  • Card grid pattern — render N skeleton cards (matching your actual grid column count) each with an avatar-shaped image placeholder and 2–3 paragraph lines. Use Skeleton.Avatar with shape="square" for rectangular image thumbnails.
  • Form pre-fill pattern — show label-height (10px) skeleton lines above full-width input-height (40px) blocks for each field. Match the exact grid layout of the form so no reflow occurs on load.
  • Detail page pattern — for a detail/header section: large avatar circle + title skeleton at 38% width + 3-line paragraph. Below the fold, use smaller skeletons for KPI tiles and secondary sections.
Anti-patterns
  • ❌ Equal-width paragraph rows — all rows at 100% looks like a bar chart, not text.
    ✅ Fix: use ['100%', '92%', '61%'] (or the Ant Design default paragraph.width).
  • ❌ Skeleton + Spinner in the same region simultaneously — creates competing loading signals.
    ✅ Fix: choose one per region. Skeleton for layout-preserving loads; Spinner for overlay/button states.
  • ❌ Skeleton that never resolves — if data fails silently, users stare at a permanently loading UI.
    ✅ Fix: implement a 10s timeout that replaces the skeleton with an error empty state and retry button.
  • ❌ Too many skeleton rows — showing 20 skeleton rows for a table implies a huge result set even when it may be empty.
    ✅ Fix: always show exactly 3 rows — this is a convention, not a preview of expected row count.
  • ❌ Skeleton without aria-busy — screen reader users get no feedback that the page is loading.
    ✅ Fix: always set aria-busy="true" on the content region and use a live region to announce completion.
