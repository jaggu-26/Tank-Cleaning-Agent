Tabs

Overview

Tabs organise related content into sections that share the same space. Only one section is visible at a time. Pelagos tabs follow the Ant Design pattern with two visual styles (Line and Card), three sizes, and placement on all four sides. Click any tab below to switch content.

Anatomy

A Tab component has two main regions: the Tab List (trigger buttons in a row) and the Tab Panel (content area). The active indicator is a 2px border on the active edge.

  1. Tab List — role="tablist" container. Horizontal flex strip with overflow-x:auto for scrollable overflow. Border-bottom: 2px --prim-grey-100.
  2. Active indicator — 2px bottom (or appropriate edge) border in --color-brand. Sits flush on the tab list border, replacing it.
  3. Tab Panel — role="tabpanel". Only the active panel is rendered/visible. Linked to its tab via aria-controls / aria-labelledby.
  4. Tab button — role="tab" with aria-selected. Font: --prim-font-weight-semibold 14px. Active: --color-brand. Inactive: --prim-grey-500.

Accessibility
ARIA Pattern

Implements the ARIA Tabs pattern. The container uses role="tablist", each trigger is role="tab", and each panel is role="tabpanel". Roving tabindex ensures only one tab is in the Tab sequence at a time.

Do / Don't
Do

  • Profile settings.

    Security settings.

    Use short, scannable tab labels (1–2 words). Users should predict panel content from the tab label alone.

Don't

  • Don't cram too many tabs (5+) with long labels. Use a Side Navigation or grouped sections instead.

Related Components
  • — Use when you have many sections requiring persistent visibility of the full navigation structure.
  • — Use for 2–3 mutually exclusive options that switch a view inline without a content panel below.
  • — Use when content has a sequential, ordered flow rather than parallel sections.

Full Example
JSX
import { useState } from 'react';
import { Tabs } from '@pelagos/react-components';

export function ProjectTabs() {
  const [activeKey, setActiveKey] = useState('overview');

  return (
    <Tabs
      activeKey={activeKey}
      onChange={setActiveKey}
      type="line"
      size="md"
      items={[
        {
          key: 'overview',
          label: 'Overview',
          children: <ProjectOverview />,
        },
        {
          key: 'team',
          label: 'Team',
          icon: <UsersIcon size={16} />,
          badge: teamCount,
          children: <TeamPanel />,
        },
        {
          key: 'settings',
          label: 'Settings',
          children: <SettingsPanel />,
        },
        {
          key: 'archived',
          label: 'Archived',
          disabled: !isAdmin,
        },
      ]}
    />
  );
}

On This Page

When to Use
  • Parallel content sections — When content is logically grouped into peer-level categories (not sequential steps) and only one needs to be visible at a time.
  • Settings pages — Profile / Security / Notifications / Billing grouped in vertical tabs with persistent navigation.
  • Detail views — A record's Overview / History / Files in a card, where switching does not require page navigation.
  • Content-heavy dashboards — Separating map, list, and chart views of the same dataset.
When Not to Use
  • Sequential processes — Use when steps must be completed in order.
  • 2–3 view-mode options — Use for compact, instant-apply view switching.
  • 5+ tabs with long labels — The strip becomes unwieldy. Use a Side Navigation or Dropdown instead.
Best Practices
  • Short labels — 1–2 words per tab. Users must predict panel content from the label.
  • Default-active the primary tab — The most commonly needed section should be active on load.
  • Keep panel count consistent — Don't add or remove tabs based on user action (use disabled, not removal).
  • Lazy-load heavy panels — Only render panel content when its tab is first activated to improve initial load.
