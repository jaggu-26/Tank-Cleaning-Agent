Steppers

Overview

Steppers (Progress Indicators) guide users through a numbered sequence of steps. They communicate where the user is in a multi-step process and how many steps remain. Pelagos provides horizontal and vertical orientations, each available on both light and dark backgrounds with identical step structure. Use the interactive Next/Back controls below.

Anatomy

Each step has a circle indicator and a text block. Between steps, a connector line signals progress. The same anatomy applies to both horizontal and vertical orientations and both colour themes.

  1. Step circle — 32×32px, border-radius: 50%. Shows step number (waiting), check icon (done), or error icon (error). Active state: --color-brand fill.
  2. Connector — 2px horizontal (or vertical) line between circles. Colour: --prim-grey-200 (waiting), --color-brand (done). Same in dark theme with adjusted opacity values.
  3. Step title — --prim-font-size-sm / --prim-font-weight-semibold. Active: --color-brand. Done: --color-text-default. Waiting: --color-text-secondary.
  4. Step description — Optional subtitle. --prim-font-size-xs / --color-text-secondary. Sits below the title on both orientations.

Interactions
TriggerBehaviour
Click "Next" buttonAdvances the current step — marks previous as done, increments active, leaves future as waiting. Fires onChange(nextIndex).
Click "Back" buttonDecrements the active step. Previous step returns to active; current step reverts to waiting.
Click step circle (if clickable)Navigates directly to that step. Useful for review flows where users revisit earlier steps.
Validation failStep remains active; an error state can be applied via status="error" on the step. Inline error messages appear in the panel below.
TabMoves focus through interactive step buttons (Next/Back or clickable circles).
Accessibility
Semantic Pattern

The step list uses role="list" with each step as role="listitem". The current step is announced with aria-current="step". Completed steps include a visually hidden "completed" text so screen readers announce both the step number and its state.

Full Example
JSX
import { useState } from 'react';
import { Steps } from '@pelagos/react-components';

const STEPS = [
  { title: 'Vessel Info',  description: 'Name & IMO'       },
  { title: 'Route Plan',   description: 'Waypoints & ETAs' },
  { title: 'Cargo',        description: 'Manifest'         },
  { title: 'Submit',       description: 'Review & confirm' },
];

export function VoyageWizard() {
  const [step, setStep] = useState(0);
  const [errors, setErrors] = useState<number[]>([]);

  async function handleNext() {
    const valid = await validateStep(step);
    if (!valid) { setErrors([...errors, step]); return; }
    setErrors(errors.filter(e => e !== step));
    setStep(step + 1);
  }

  return (
    <div>
      <Steps
        current={step}
        items={STEPS.map((s, i) => ({
          ...s,
          status: errors.includes(i) ? 'error' : undefined,
        }))}
      />

      <div style={{ marginTop: 'var(--prim-space-8)' }}>
        {step === 0 && <VesselForm />}
        {step === 1 && <RouteForm  />}
        {step === 2 && <CargoForm  />}
        {step === 3 && <ReviewPage />}
      </div>

      <div style={{ display:'flex', gap:10, marginTop:20 }}>
        <Button onClick={() => setStep(step-1)} disabled={step===0}>Back</Button>
        <Button variant="primary" onClick={handleNext}>
          {step === STEPS.length-1 ? 'Submit' : 'Next'}
        </Button>
      </div>
    </div>
  );
}
HTML
<gs-steps [(current)]="step">
  <gs-step *ngFor="let s of steps; let i=index"
    [title]="s.title"
    [description]="s.description"
    [status]="errors.includes(i) ? 'error' : undefined">
  </gs-step>
</gs-steps>

When to Use
  • Multi-step forms — Registration, booking, checkout, onboarding wizards where tasks must be completed in a defined order.
  • Process tracking — Showing where a shipment, application, or order is in a workflow without user control (display-only mode).
  • Guided configuration — Complex setup wizards (e.g., vessel registration, route planning) where each step validates before proceeding.
  • Dark background contexts — Dashboards, map views, or full-screen dark UIs that need the stepper to match the surface colour.
When Not to Use
  • Parallel non-sequential sections — Use when any section can be accessed in any order.
  • Simple 2-step process — A stepper for 2 steps adds overhead. Use a simple form with a summary step or a dialog instead.
  • Progress indication only — Use a Progress Bar when you only need percentage completion, not labelled step milestones.
Best Practices
  • 3–6 steps is the sweet spot — Fewer feels unnecessary; more becomes overwhelming. Break complex processes into grouped stages if needed.
  • Validate before advancing — Never silently skip validation. If a step is invalid, show the error state on the circle and keep the user on that step.
  • Allow going back — Unless there is a strong security reason, users should be able to review and edit previous steps.
  • Use the same structure for light and dark — Do not add or remove steps based on theme. Identical step count and labels on both variants ensures consistency.
  • Persist state across steps — Do not reset form values when navigating backward. Use a form state manager or controlled inputs.
