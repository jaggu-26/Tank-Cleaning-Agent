Checkbox

Overview

Checkboxes let users select one or more independent options from a set. Unlike radio buttons, any number of checkboxes in a group can be selected at once — each operates independently. Use them in forms, settings panels, filter bars, and bulk-selection tables where multi-select is expected.

Variants

The Checkbox has one visual variant — a single form factor with two selection values: unchecked and checked. Visual differentiation is achieved through color and the checkmark icon rather than structural variant families.

Anatomy

The checkbox is a 24×24px touch target containing a 16×16px visual control. A 2px gap separates the box from the text label.

  1. Touch target — 24×24px invisible hit area. Meets Apple HIG (44px achieved via outer padding) and MD minimums. Always present.
  2. Control (inner box) — 16×16px visual square with 4px border-radius. Shows white background + gray border when unchecked; brand blue fill + white checkmark when checked. Required.
  3. Gap — 2px spacing between box and label. From --spacing/spacing-2.
  4. Label — 14px/Regular/20px line-height text in #001e4c (navy). Required for accessible usage; icon-only checkboxes must have aria-label.
States

Twelve states cover the full interaction matrix: three selection values (unchecked / indeterminate / checked) × four interaction states (Default, Hover, Focus, Disabled). The indeterminate state is set via input.indeterminate = true in JS — use it for "select all" patterns when only some children are selected.

Focus Indicator

Unchecked focus: 1.5px solid #5fa5f9 ring rendered as box-shadow around the 16×16px control. Checked focus: 1.5px solid #5fa5f9 outline around the entire label component. Both meet WCAG 2.4.11 enhanced focus visibility at 3:1+ contrast on white.

Touch Target

The outer gs-cb-box wrapper is 24×24px. The full label row (box + text) forms the clickable area, typically exceeding 44px in width and the 32px minimum height for most labels — satisfying WCAG 2.5.8.

Complete registration
Do / Don't
Do

  • Always provide a visible, descriptive label alongside the checkbox.

  • Use checkboxes for multi-select scenarios where selections are independent.

  • Disable with a tooltip or explanation when a feature is unavailable.

  • Align box to the top when label text wraps to multiple lines.

Don't
  • ← no label

    Don't use icon-only checkboxes without an aria-label. Screen readers will announce nothing meaningful.

  • Don't use checkboxes for single-choice selections — use radio buttons instead.

  • Don't use all-caps labels. Use sentence case for all checkbox labels.

  • Yes
    No

    Don't use Yes/No checkbox pairs — use a Toggle or Radio group for binary choices.

Related Components
  • — Use when only one option from a group can be selected at a time (mutually exclusive).
  • — Use for filter toggles in toolbars where selected state persists and chips are visible at all times.
  • — Use for binary on/off settings that take immediate effect (no Save needed), especially on mobile.
  • — Pair checkboxes with text fields when the option requires free-form input upon selection.

Quick Access

1

Overview

The Checkbox component is a Pelagos wrapper on top of Ant Design's Checkbox. All interactive behaviours — toggle, indeterminate marker, keyboard activation, focus ring, disabled state, wave animation — are delegated entirely to AntD. Pelagos design tokens are injected via a scoped ConfigProvider in checkboxTheme.js so they never bleed into the global theme. Refs are forwarded to the AntD Checkbox for form library compatibility.

The React component uses React.forwardRef. Pass checked + onChange for controlled mode, or defaultChecked for uncontrolled. All AntD Checkbox props pass through via ...rest.

The Angular component is a standalone component implementing ControlValueAccessor — it works with [(ngModel)] and reactive FormControl with no extra wiring. Tokens are applied via NZ_CONFIG at bootstrap.

Theming

Colours are injected entirely through AntD's token system — not CSS variables. Override the scoped ConfigProvider by importing getCheckboxTheme and merging your values on top.

jsx · React — override brand colour
import { ConfigProvider } from 'antd';
import { Checkbox } from '@pelagos/components/primitives/checkbox';
import { getCheckboxTheme } from '@pelagos/components/primitives/checkbox';

// Merge your overrides on top of the Pelagos theme
const customTheme = {
  ...getCheckboxTheme(),
  token: {
    ...getCheckboxTheme().token,
    colorPrimary: '#0052CC',  // override brand blue project-wide
  },
};

function MyCheckbox(props) {
  return (
    <ConfigProvider theme={customTheme}>
      <Checkbox {...props} />
    </ConfigProvider>
  );
}
typescript · Angular — NZ_CONFIG at bootstrap
import { NZ_CONFIG, NzConfig } from 'ng-zorro-antd/core/config';
import { getCheckboxTheme }    from '@pelagos/components/primitives/checkbox';

const theme = {
  ...getCheckboxTheme(),
  token: {
    ...getCheckboxTheme().token,
    colorPrimary: '#0052CC',  // override brand blue
  },
};

bootstrapApplication(AppComponent, {
  providers: [
    { provide: NZ_CONFIG, useValue: { theme } as NzConfig },
  ],

Token override chain: colorPrimary → #1852FE (via globalTokens) drives checked fill, checked border, and focus ring. Overriding colorPrimary in the merged theme cascades to all three states automatically.

Full Working Example

jsx · Checkbox list with label / no-label variants
import { useState } from 'react';
import { Checkbox, Button } from '@pelagos/components';
import '@pelagos/foundations/index.css';

const OPTIONS = [
  { id: 'a', label: 'Option A', default: true },
  { id: 'b', label: 'Option B', default: true },
  { id: 'c', label: 'Option C', default: false },
  { id: 'd', label: 'Option D', default: false, disabled: true },
];

export default function CheckboxList() {
  const [values, setValues] = useState(
    Object.fromEntries(OPTIONS.map(o => [o.id, o.default]))
  );

  const handleChange = (id, val) =>
    setValues(v => ({ ...v, [id]: val }));

  return (
    <section>
      <h2>Options</h2>

      {/* With label */}
      {OPTIONS.map(opt => (
        <Checkbox
          key={opt.id}
          label={opt.label}
          checked={values[opt.id]}
          disabled={opt.disabled}
          onChange={(e) => handleChange(opt.id, e.target.checked)}
        />
      ))}

      {/* Without label — aria-label required */}
      <Checkbox
        aria-label="Select row"
        checked={values.a}
        onChange={(e) => handleChange('a', e.target.checked)}
      />

      <Button variant="primary" onClick={() => onSave(values)}>
        Save
      </Button>
    </section>
  );
}

Quick Access

When to Use
  • Multi-option settings — Notification preferences, feature toggles, export options. Any panel where the user can enable or disable multiple independent features.
  • Filter sidebars — Vessel type, port, status filters where multiple values can be active simultaneously. Checkboxes let users combine filters freely.
  • Bulk table selection — Row selection in vessel or port call tables. A header "select all" checkbox with individual row checkboxes is the standard pattern.
  • Form agreements — Terms of service, consent declarations, newsletter sign-up. Each agreement is independent, so checkboxes are appropriate.
  • Grouping related options — Permissions (read / write / delete), data export fields (name / IMO / berth), where each option has equal weight and can be combined.
  • Optional form fields — "Include in report", "Send copy to manager" — secondary options that do not block form submission.
When Not to Use
  • Single-select from a group — Use instead. If the user must pick exactly one from a list ("Arrival" or "Departure"), radios communicate mutual exclusivity that checkboxes do not.
  • On/Off setting with immediate effect — Use instead. A toggle communicates live state and takes effect without a Save action.
  • Filter chips in a bar — Use instead. Chips are more compact and visually prominent in dense toolbars.
  • Confirming destructive actions — Use a inside a modal. A checkbox confirmation ("I understand this will delete 200 records") adds friction without clarity.
  • When the label doesn't fit on one component — If the full context requires more than a single sentence, use an expandable or modal pattern with a primary action button.
Content Hierarchy
Label Writing Rules
  • Use a noun or verb phrase — "Email alerts", "Enable notifications", "Accept terms". Avoid vague labels like "Option A".
  • Sentence case — "Enable auto-save" not "Enable Auto-Save" and not "ENABLE AUTO-SAVE".
  • Describe the on-state — Write the label as if the checkbox is checked. "Receive email updates" means "if checked, you will receive email updates."
  • Keep it short — 2–6 words ideal. Labels longer than 12 words should be reconsidered (use helper text or a linked policy page instead).
  • No trailing punctuation — Don't end labels with a period. Exception: multi-sentence labels where the first sentence ends mid-label.

Common Mistakes
❌ Mistake

Using a checkbox for a binary Yes/No choice (two checkboxes: "Yes" and "No").

✅ Fix

Use a Radio Button group. Two checkboxes for Yes/No are confusing because both could theoretically be checked. Radios communicate mutual exclusivity.

❌ Mistake

A toggle that requires a Save button — using Toggle for settings that don't take immediate effect.

✅ Fix

Use Checkbox in a settings form that has an explicit Save action. Toggle implies immediate effect; if the user must save, use Checkbox.

❌ Mistake

Skipping the label and placing helper text as the only description, leaving the bare checkbox with no adjacent text.

✅ Fix

Always provide a visible label or aria-label on the checkbox itself. Helper text is supplementary — it cannot replace the label.

❌ Mistake

Using a disabled checkbox to convey that a feature is "coming soon" with no explanation.

✅ Fix

Disabled controls must be accompanied by visible context — a tooltip, an adjacent note, or a badge. "Coming soon" and "enterprise only" should be explained inline.

❌ Mistake

Using checkboxes inside a radio group pattern — mixing checked states that were meant to be exclusive.

✅ Fix

Decide first: can the user pick multiple values? → Checkbox. Must pick exactly one? → Radio. Don't use checkboxes with code that unchecks others when one is checked — that's a radio pattern, use the right component.
