Tooltip

Overview

Tooltips are small, transient informational pop-overs that appear when users hover over, focus on, or tap a trigger element. They surface supplementary context — labels for icon-only buttons, keyboard shortcuts, truncated text — without cluttering the UI. Pelagos tooltips support 12 placement positions, a dark and a light theme, and optional rich content (title + description).

Anatomy

A tooltip has two parts: the trigger element (any interactive or focusable element) and the floating content panel with an optional directional arrow.

  1. Tooltip panel — Floating container. Background: #1e293b (dark) / #fff (light). Border-radius: 6px. Padding: 6px 10px. Max-width: 240px.
  2. Label — 12px / 500 weight text. Single line preferred; wraps to max-width if needed. Color: #fff (dark theme), #1e293b (light theme).
  3. Arrow — 10×5px directional caret pointing toward the trigger. Optional; omit for placements without clear direction. Color matches panel background.
  4. Trigger element — Any interactive or focusable element: button, link, icon, input. The tooltip panel is positioned relative to this element with an 8px gap.
Variants

Two themes and 12 placement positions. Use dark theme (default) on light backgrounds; use light theme when the trigger is on a dark or coloured surface.

Accessibility
Semantic Element

The tooltip panel uses role="tooltip". The trigger element references it via aria-describedby so screen readers announce the tooltip text after the trigger label. The panel is rendered in the DOM but visually hidden when not active — not removed — ensuring screen readers can access it.

Overview

Wrap any element with <Tooltip>. The child element becomes the trigger. Use the title prop for label text and placement for position. Built on Floating UI for automatic overflow detection.

Use the gsTooltip directive on any element. Pass [gsTooltipTitle] for label text and [gsTooltipPlacement] for position.

When to Use
  • Icon-only buttons and controls — Provide a visible label on hover/focus so sighted keyboard users and screen reader users can identify the action without decoding the icon alone.
  • Truncated text in tables or cards — Show the full string in a tooltip when overflow is ellipsed due to constrained layout.
  • Keyboard shortcuts — Surface the shortcut key combo in the tooltip of a toolbar button (e.g., "Bold — ⌘B").
  • Supplementary labels on form inputs — A short clarification alongside an input field label, where inline helper text would be too verbose.
  • Status badges or colour indicators — Provide semantic meaning when colour alone is used to convey status (e.g., a coloured dot with a tooltip "Active").
When Not to Use
  • Long-form or interactive content — Use instead. Tooltips cannot contain clickable links, form fields, or multi-paragraph text.
  • Error messages on inputs — Error text should be persistent and inline beneath the field, not hidden behind hover. Users on mobile may never discover hover-only errors.
  • Critical information the user must act on — If the user must read and respond to content, use a .
  • On touch-only devices where hover is absent — If your primary audience is mobile, consider whether an inline label or persistent secondary text is more accessible.
Best Practices
  • Keep label text brief — One short phrase or sentence maximum. If you need more, use a popover.
  • Always pair tooltips with aria-label on icon-only controls — aria-describedby supplements the button label; it doesn't replace it. Icon-only buttons still need aria-label for screen readers that read the button label first.
  • Don't disable the 300ms hover delay — The delay prevents tooltip flicker as users move the cursor across the UI. Reducing it below 200ms causes poor UX.
  • Prefer placement="top" or "bottom" — These positions are least likely to obscure surrounding content and work better on narrow viewports where side placements clip.
  • Test on touch devices — Validate the tap-then-activate flow on iOS and Android to ensure icon-only buttons are still reachable without the tooltip.
Patterns
  • Icon Action Bar — Place tooltips on each icon button in a toolbar or table action row with placement="bottom" so tooltips open downward and don't overlap the toolbar.
  • Truncation Reveal — Use placement="top" and set title={fullText} on the truncated element. Combine with an onMouseEnter check to only show the tooltip when text is actually truncated.
  • Shortcut Hint — Format as rich content: bold action name on the first line, keyboard shortcut in a <kbd> element on the second.
  • Disabled Button Explanation — Wrap a disabled button in a non-disabled <span> to show a tooltip explaining why the button is disabled.
Anti-patterns
  • ❌ Putting required info only in a tooltip — Hover-only content is inaccessible on touch devices and may be missed.
    ✅ Fix: Use inline helper text for important guidance; use tooltip only for supplementary context.
  • ❌ Tooltip on a non-focusable element (e.g., plain div) — Keyboard users can't reach it, violating WCAG 2.1.
    ✅ Fix: Ensure the trigger is natively focusable (button, a, input) or add tabindex="0" and an appropriate role.
  • ❌ Multi-paragraph text inside a tooltip — Tooltips are for labels, not documentation. Long content overflows and becomes unreadable.
    ✅ Fix: Use a Popover for rich or interactive content.
  • ❌ Tooltip with zero delay on a dense button bar — Tooltips fire on every button as the cursor sweeps across, causing visual chaos.
    ✅ Fix: Keep the 300ms show delay. Set hide delay to 100ms for snappy dismissal.
