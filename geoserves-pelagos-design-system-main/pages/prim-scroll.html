Scroll

Overview

Pelagos uses a thin custom scrollbar — 6 px track, pill-shaped handle — consistent across vertical and horizontal axes. On hover the container highlights the handle and expands the track from 6 px → 10 px for easier grabbing. Two themes (light / dark) map to the Figma variants.

Anatomy

A scrollbar has two visual parts: the track (the groove) and the handle (the draggable thumb). Both are pill-shaped. The handle position indicates scroll position; its size indicates the proportion of visible content.

  1. Track — The groove. 6 px wide, 100 px border-radius. Light: #e2e8f0. Dark: transparent.
  2. Handle (thumb) — The draggable part. 6 px wide (default), expands to 10 px on hover. Colour: #94a3b8 default → #64748b hover.
  3. Border-radius — Both track and handle use 100px (pill) per Figma spec.

Hover Expand

The scrollbar is invisible by default and appears instantly when the cursor enters the container — driven by pure CSS :hover (no JS delay). The track also expands from 6 px → 10 px on hover for easier grabbing; this width change uses a JS class (.gs-scroll--hover) because CSS transitions cannot animate ::-webkit-scrollbar-width directly.

Default — 6 px
Hover — 10 px

The 4 px width gain significantly improves touch and trackpad usability on dense data tables and sidebars without visually competing with content when idle.

Live — hover the container to see it expand

Hover anywhere over this container — the scrollbar expands from 6 px to 10 px.

This makes it easier to grab and drag, especially on high-density displays or when using a mouse with a fine cursor.

The colour also darkens slightly as an additional visual affordance.

On mouseleave the bar returns to 6 px.

Overview

The Scroll React component wraps any content in a container with Pelagos-styled scrollbars. The hover-expand (6→10px) is handled internally — no extra JS needed.

Apply .gs-scroll + direction + theme modifier classes to any overflow container. The page's gsScrollInitHover() function attaches the expand listeners. Call it after inserting the element into the DOM.

Hover Expand — Implementation

::-webkit-scrollbar-width cannot be CSS-transitioned. The expand is achieved by toggling a class on mouseenter/mouseleave. The React component handles this internally. For HTML/Angular, call gsScrollInitHover().

JSX
// React — expand is built-in via useState in Scroll.jsx
<Scroll direction="vertical" maxHeight="300px">
  ...content...
</Scroll>

// CSS custom properties to retheme the expand width:
.my-scroll {
  --scroll-size:       6px;   /* default */
  --scroll-size-hover: 10px;  /* hover-expanded */
}
JS
// Bind expand listener to all .gs-scroll elements on the page
function gsScrollInitHover() {
  document.querySelectorAll('.gs-scroll').forEach(function(el) {
    if (el.dataset.scrollInit) return;
    el.dataset.scrollInit = '1';
    el.addEventListener('mouseenter', () => el.classList.add('gs-scroll--hover'));
    el.addEventListener('mouseleave', () => el.classList.remove('gs-scroll--hover'));
  });
}

// Call after DOM is ready or after dynamic insertion
gsScrollInitHover();

When to Use
  • Data tables with many columns — horizontal scroll keeps the full-width layout while allowing the user to pan right to see more columns.
  • Long log feeds or timelines — vertical scroll in a fixed-height container (e.g. AIS event log, voyage history panel).
  • Sidebars with overflowing nav items — use autoHide=true so the scrollbar only appears on hover, keeping the sidebar clean.
  • Dark-themed panels — use theme="dark" so the track doesn't create a visual band in dark surfaces.
  • Modal bodies with long forms — scroll the modal body independently of the page, preventing the viewport from shifting.
When Not to Use
  • Full-page scroll — the body scroll should use the browser default. Only constrain overflow inside UI regions like panels, cards, and modals.
  • Short content that rarely overflows — adding a scroll container adds a visual boundary. Use only when overflow is likely or guaranteed.
  • Touch-primary interfaces — custom thin scrollbars are hard to grab on small touchscreens. Consider a visible grab handle or pagination instead.
Best Practices
  • Always set a max-height or max-width — the scroll container needs a bounded dimension to trigger overflow. Without it, .gs-scroll does nothing.
  • Add tabindex="0" — makes the region keyboard-focusable so users can scroll with arrow keys. Required for WCAG 2.1 compliance.
  • Use autoHide sparingly — hiding the scrollbar by default removes the affordance that content is scrollable. Only use it in dense UIs where the scrollbar itself creates visual clutter.
  • Pair with a fade gradient — add a CSS gradient mask at the bottom/right edge of the container to visually signal that content continues beyond the visible area.
  • Call gsScrollInitHover() after dynamic inserts — in Angular/HTML, any element added after the initial page load won't have the expand listeners until you call the function again.
Anti-patterns
  • ❌ Nesting scroll containers — a scrollable region inside another scrollable region confuses users about which one the mouse-wheel controls.
    ✅ Fix: Only the innermost container should scroll. Ensure the outer container does not overflow.
  • ❌ Hiding scroll on the body and using a custom scroll everywhere — creates inconsistency and breaks browser back/forward navigation.
    ✅ Fix: Only use .gs-scroll on bounded panels and sidebars.
  • ❌ Forgetting aria-label on scrollable regions — screen readers can't announce what's in the scrollable region.
    ✅ Fix: Always pair role="region" with a descriptive aria-label.
